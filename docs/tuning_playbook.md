# Strict Tuning Playbook (Log-Driven)

This playbook gives a deterministic, repeatable procedure to tune reward weights,
algorithm settings, and hybrid gains using logs generated by this repository.

It is designed to avoid ad-hoc tweaking.

## 1) Required Outputs per Tuning Iteration

For each candidate run, produce both:
- Evaluation summary JSON (time-domain behavior).
- Frequency summary JSON (band attenuation behavior).

Commands:

```powershell
python scripts/eval.py `
  --algo sac `
  --model-path runs/candidate/final_model `
  --env-config configs/env.yaml `
  --episodes 20 `
  --save-json runs/candidate/eval_summary.json `
  --record-first-episode runs/candidate/rollout_ep0.npz

python scripts/analyze_frequency.py `
  --rollout-npz runs/candidate/rollout_ep0.npz `
  --band-min-hz 100 `
  --band-max-hz 400 `
  --save-json runs/candidate/frequency_summary.json
```

Use deterministic evaluation unless you are specifically testing exploration effects.

## 2) Metrics You Must Track

From `eval_summary.json`:
- `termination_rate`
- `accel_rms_mean`
- `pos_rms_mean`
- `chatter_rms_mean`
- `peak_abs_torque_mean_nm`

From `frequency_summary.json` per axis:
- `band_mean_mag_db`
- `band_peak_mag_db`
- `band_peak_freq_hz`
- `torque_rms_nm`

Maintain one tuning table where each row is one run/config snapshot.

## 3) Hard Gates (Do Not Optimize Past These)

Gate A: Stability
- `termination_rate == 0` over 20 eval episodes.

Gate B: Safety
- `peak_abs_torque_mean_nm` and axis `torque_rms_nm` must stay under hardware-safe bounds.

Gate C: Pointing
- `pos_rms_mean` must not regress more than 10% from your current accepted baseline.

Only compare vibration attenuation among runs that pass all gates.

## 4) Baseline Setup

1. Train and evaluate SAC baseline with current defaults.
2. Save outputs as reference:
- `runs/baseline/eval_summary.json`
- `runs/baseline/frequency_summary.json`
3. Mark baseline as `B0` in your tuning table.

All later decisions are relative to `B0` unless replaced by a better accepted baseline.

## 5) Reward Weight Tuning Sequence

Tune in this order and do not change more than one weight group per iteration.

### Stage 1: `w_a` (acceleration weight)

Goal:
- Reduce `band_mean_mag_db` and `band_peak_mag_db` in 100-400 Hz.

Adjustment rule:
1. If attenuation is weak and torque is within limits, increase `w_a` by +20%.
2. If torque rises too much with minimal attenuation gain, revert and proceed to `w_c`.

Acceptance for stage move-on:
- At least 2-3 dB improvement in average band magnitude on the worst axis,
  without violating hard gates.

### Stage 2: `w_c` (chatter weight)

Goal:
- Reduce control aggressiveness while preserving achieved attenuation.

Adjustment rule:
1. If `chatter_rms_mean` or torque RMS is high, increase `w_c` by +25%.
2. If attenuation degrades >1.5 dB, partially roll back (`w_c` halfway to previous value).

Acceptance for stage move-on:
- Torque/chatter within limits, and attenuation regression <=1.5 dB from best stage-1 result.

### Stage 3: `w_p` (position weight)

Goal:
- Recover/maintain pointing precision with minimal vibration penalty.

Adjustment rule:
1. If `pos_rms_mean` is high, increase `w_p` by +15%.
2. If attenuation worsens noticeably (>1 dB) and pointing gain is marginal, revert.

Acceptance:
- Pointing target met with no hard-gate violation and minimal attenuation loss.

## 6) Algorithm-Level Tuning

After reward weights are stable, tune algorithm parameters.

### SAC-first strategy

Adjust one item at a time:
1. `total_timesteps`: +25% if learning still improving near run end.
2. `batch_size`: test 256 vs 512 based on stability and throughput.
3. `net_arch`: `[256,256]` to `[384,384]` only if underfitting signs remain.

Keep `gamma` and `tau` fixed initially unless instability clearly indicates otherwise.

### DDPG comparison

Use DDPG as benchmark/control variant:
- Match environment and evaluation process exactly.
- Tune `action_noise_sigma` only after reward and baseline comparisons are consistent.

Decision rule:
- Prefer model with better worst-axis `band_peak_mag_db` at matched safety/pointing gates.

## 7) Hybrid PID + RL-Delta Tuning (Sim-to-Real Stage)

Enable:
- `hybrid_control.enabled: true`

Then tune with this strict sequence:

1. Start with small `rl_delta_scale` (already 0.25 defaults).
2. Tune PID (`kp`, `kd`) to ensure stable low-frequency behavior without RL contribution spike.
3. Increase `rl_delta_scale` in +0.05 increments only if attenuation gain is needed.
4. Add/adjust `ki` last for bias rejection; keep integral limit conservative.

Rules:
- If oscillation appears immediately after raising `rl_delta_scale`, revert one step.
- If low-frequency drift persists with stable high-frequency attenuation, increase `w_p` or `ki` slightly.

## 8) Iteration Template (Use Every Time)

For iteration `k`:
1. Edit config by one controlled change.
2. Train to same budget (or planned budget increase).
3. Evaluate and record logs.
4. Compare against current accepted baseline.
5. Accept or reject based on hard gates + improvement threshold.
6. Document reason and next single change.

This keeps causality clear and avoids confounded tuning.

## 9) Recommended Decision Thresholds

Use these practical defaults and tighten later:
- Improvement threshold: >=2 dB reduction in worst-axis band peak OR >=10% lower `accel_rms_mean`.
- Regression tolerance: <=1 dB attenuation loss if safety/pointing significantly improve.
- Stability requirement: zero terminations in 20 deterministic episodes.

## 10) Example Change Log Format

Keep `runs/tuning_log.md` with entries:
- Run ID
- Exact config delta
- Eval summary (key metrics)
- Frequency summary (worst-axis peak/mean)
- Accept/Reject + reason
- Next action

Example:
- `R07`: `weights.accel 1.00 -> 1.20`
- Result: worst-axis peak -2.8 dB, torque_rms +6%, no terminations
- Decision: Accept
- Next: increase `weights.chatter` by 20%

## 11) Failure Patterns and Corrective Actions

Pattern: terminations appear after improving attenuation.
- Action: reduce action aggressiveness (`w_c` up, `rl_delta_scale` down, or smaller LR).

Pattern: low torque RMS but weak attenuation.
- Action: increase `w_a` or reduce `w_c` slightly.

Pattern: good attenuation, poor pointing.
- Action: increase `w_p` or retune PID baseline in hybrid mode.

Pattern: run-to-run variance too high.
- Action: increase episodes in evaluation and compare mean + variance, not single values.

## 12) Exit Criteria for Hardware Trial

Proceed to hardware/HIL only when all are true:
- Stable (`termination_rate = 0`) across repeated evaluations.
- Consistent attenuation gain vs baseline in target band.
- Torque and chatter within your motor thermal/current envelope.
- Pointing error within mission threshold.
- No contradictory behavior across axes.
